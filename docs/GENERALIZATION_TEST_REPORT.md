# 泛化測試報告：Character-to-Spine 對陌生角色的實際能力

2026-11-24，分支 `feat/character-to-spine-mvp`。數字與等級都來自 `docs/GENERALIZATION_TEST_MATRIX.md`，該矩陣由 `python scripts/generalization.py report` 依 `output/generalization/results.json` 產生。預覽都是 Python Simulation Preview，不是 Spine 算圖；Spine 正式輸出（`.spine`、往返、Editor 可編輯性）因只有試用版仍是 BLOCKED（K-01），不影響本報告的等級。

## 結論

本階段的目標，是證明系統能處理沒看過的角色。結論如下：

- **Skill 能被自然語言觸發，但還不能獨立運作。** 9 張陌生角色圖都由全新的 Claude Code session 以自然語言觸發 Skill，Agent 自己看圖寫出 `parts.json` 並執行 `c2s`，使用者不需要手寫任何東西。測了 4 種說法：中文、另一種中文、英文、間接描述。限制有兩個：
  - `c2s` 由本專案的 `.venv` 提供。
  - `SKILL.md` 第 6 步引用的 `scripts/visual_report.py` 不在 Skill 資料夾裡。最終輪 9 次中有 7 次跑到沙盒外的本專案找它，所以沙盒並沒有隔離專案。偵測器沒有發現讀到答案，但「Skill 可在別人的電腦獨立運作」尚未驗證。
- **完整自動成功（PASS）是 0 張。**
  - 開發集第一次盲測：成功 0/5，可處理（PASS 或 PARTIAL）1/5。
  - 保留集（所有修改完成後才第一次執行）：成功 0/4，可處理 1/4。這唯一的 PARTIAL（H3）也有骨架顛倒的結構錯誤（K-28），只是在預覽中看不出來；空手的動作量 2.2%，只比 2% 門檻多一點。所以這個 1/4 很脆弱。
  - 開發集修改後是 0/5、3/5，但這組圖用來改過 Skill 與程式，**不是泛化證據**。
- **「錯誤但看似成功」沒有完全避免。** 每個需要補畫的部件都列在修補清單上。最終輪 9/9 的最後回覆都依 `validation_report.json` 說明「還沒完成」。但有兩個嚴重問題，自動檢查沒有抓到：
  - **H4 坐姿角色只剩整體跳動。** session 有提醒「整個角色往上跳、鞋子離地，對坐姿可能不自然」，但沒有指出四肢幾乎不動，只把它列為「其他提醒」，沒有當成失敗。
  - **H2 拿夾板的手臂骨架上下顛倒。** session 完全沒有提到。
- **已知的失敗原因有四類。** 成因是依異常影格與目視推測的，尚未用修正版驗證。
  1. 品質檢查把「碰巧接觸的部件圍出的背景」判為破洞或縫隙，自我修正因此縮小手臂或留下未解異常（K-24）。最終狀態出現在 C、H1、H2、H4；E 的基準也有。
  2. 手拿著小物件時，骨架上下顛倒（K-28）。出現在 C、H2、H3。
  3. 持物或被遮擋的手臂動作量不足（D）。
  4. 坐姿角色套用站姿的動畫模板（H4）。

  前兩類是程式的共通問題，留到下一階段修。原因是保留集已經用目前的程式跑完，現在修改等於拿保留集來調參。

## 2. 方法：凍結、盲測、保留集

1. **先凍結再測。** 門檻在既有角色與合成角色上校準後，於 `9788457` 提交，之後才對新圖執行 `c2s`。後續每一次標準變更都登記在 manifest 的 `criteria_changes`，共 7 筆，含原值、新值與理由。矩陣的所有等級都用最新登記的同一套規則重算。
   - 基準依當時的目視是可處理 2/5（提交 `38e3c72` 的訊息）。依後來凍結的目視判準重判，B 的關節從 MINOR 改為 BAD，所以變成 1/5。這是看到結果後的收緊，已登記。
   - 保留集第一次執行時，執行器因為漏建輸出目錄而在啟動 session 前中止，沒有產生任何分析。修正執行器（沒有改 `src/`）後重跑，這才是保留集真正的第一次執行。
2. **Agent 自己寫 `parts.json`。** 每張圖開一個全新的 `claude -p` session，提示只有一句話與檔名。第一輪在專案根目錄執行時，紀錄顯示 session 讀了案例描述與其他答案（見第 4 節），所以改在只有 `SKILL.md` 與圖片的沙盒執行，最後一輪的沙盒放在 repo 外。
3. **來源查核。** 每份 `parts.json` 都和舊角色、合成角色及其他案例比對多邊形，9 張全部 PASS。凍結版的規則把 C 的 4 點多邊形判為與 D 雷同，因為同長寬比的四邊形縮放後本來就相同。新版規則是「逐點相同或只平移後殘差 < 3px；允許縮放的比對只用於 6 點以上的多邊形」。C 的等級在兩版規則下相同（FAIL）。
4. **獨立審查。** 基準結果出來後，由同模型的子代理做對抗式審查。採納的項目：
   - 撤回一個事後放寬的豁免。
   - 收緊「只剩跳動」的定義。
   - 凍結目視判準，目視紀錄綁定驗收圖的 sha256。
   - 新增保留集。

   未採納的項目與理由：不使用另一份乾淨的 Claude 設定目錄，因為登入憑證存在使用者設定裡。
5. **獨立 QA。** 報告初稿完成後，另一個子代理唯讀核對每個數字、重算判定與來源查核，並在 HEAD 重跑 pytest（147 passed）。它指出 14 處不符，包括兩個事實錯誤：H4 的 session 其實有提醒坐姿跳動；Skill 沙盒會跑到專案找 `visual_report.py`。這 14 處已全部修正於本版。
6. **自動量測與目視分開記錄。** 目視依凍結的判準清單（manifest 的 `criteria.visual_rubric`）判 OK、MINOR、BAD。基準輪由我（Agent）目視；最終輪由兩個沒看過先前判斷的子代理分別目視開發集與保留集。全部都是同一家模型，**使用者目視欄目前都是 NOT_TESTED**。

## 4. 自動完成與需要人工的部分

**自動完成（9/9）：**

- 去背檢查與格線圖。
- Agent 看圖寫 `parts.json`：部件、遮擋順序、pivot、`attach`、`absent`。
- 切出透明分層、建立骨架。
- 產生 Idle 與 Happy，循環首尾一致（9/9）。
- 逐格品質檢查與自我修正。
- 輸出 Spine JSON。
- 產生修補清單與修補優先順序。

**一定需要人工：**

- 補畫被遮擋的部件。每張圖 0 到 6 個（B 沒有），清單見各案例的 `repair_tasks.md`。
- 正式的 Spine 匯入（需要完整版）。

**`--replace` 匯回**（任務 9.1，實測）：把 A 的 body 換成程式產生的替代圖。替代圖存進圖片旁的 `gen_a.overrides/`，重跑後圖層逐像素相同，body 從需人工清單移除，`setup_pose` 仍然 PASS。這只驗證了機制，不代表補圖品質。

**Skill session 讀了不該讀的檔案**（K-21）。以下全部發生在專案根目錄那幾輪；沙盒輪的 20 次 session（6＋5＋9）都沒有讀到答案。

| 專案根目錄、未防護 | B、C 讀了 manifest 的案例描述；D 讀了 C 的 `parts.json`；E 讀了 A 的；A 的 slash 讀了 B 的 |

## 7. 目前真正支援的角色類型

依實際證據，**沒有一種類型能完全自動完成（PASS）**。

**盲測證據**（開發集第一次盲測與保留集）中能處理到 PARTIAL 的只有兩張：

- A：正面 Q 版，站姿，雙手下垂。
- H3：拿書的人形，但有 K-28 的結構錯誤。

保留集裡同樣是站姿正面人形的 H1 是 FAIL（K-24，推測）。

**只有開發集修改後才達到 PARTIAL、不是泛化證據的類型：**

- 3/4 側面、長裙蓋住雙腳的人形（B，以 `absent` 宣告，腳不動）。
- 雙足擬人動物（E）。
- 有地面影子的角色（E，`role: ground`）。

所以目前能說的是：站姿、四肢不碰其他部件、不拿小物件的人形角色，**可能**處理到 PARTIAL，但盲測樣本只有 A 一張成功處理、H1 一張失敗。

## 10. Skill v1.0 標準化前要解決的問題與建議

**必須先修的程式問題（依影響排序）：**

1. **K-24 破洞與縫隙的誤判。** 候選修法：只把「初始姿勢是不透明、動畫中變透明」的像素算成破洞（扣掉 hip 位移），縫隙只看結構上的關節。修完後必須用**新的**保留集驗證，H1–H4 已經用過了。
2. **K-28 持物骨架。** 區分「抱著」（道具帶手，例如樂器）與「拿著」（物件跟手）。可以在 `parts.json` 加一個明確的欄位，不要從面積去猜。
3. **非站姿的動畫模板**，或讓 Skill 引導 Agent 對坐姿宣告 `unsupported`。
4. **K-23。** 持物手臂也要有動作量下限，或改量整個上半身；`absent` 要有可驗證的依據。

**Skill 本身：**

- **觸發。** 9/9 由自然語言觸發，`/character-to-spine` 有間接證據（headless 模式不記錄被展開的 slash 提示）。
- **失敗回報。** 最終輪 9/9 的最後回覆都依 `validation_report.json` 說明還沒完成，並列出需人工的部件。但 session 主要只能回報檢查器抓得到的問題：
  - H4 只提醒「跳起來對坐姿可能不自然」，沒有當成失敗。
  - H2 的骨架顛倒完全沒有提到。

  標準化時要讓這兩類問題能被自動偵測，或至少讓 Agent 在回報前看一次驗收圖。
- **Skill 自足性。** `SKILL.md` 引用的 `scripts/visual_report.py` 要放進 Skill 或做成 `c2s` 子命令；`c2s` 要能獨立安裝。這兩點完成前，沙盒實測無法真正隔離專案（最終輪 9 次中 7 次跑到專案目錄）。
- **語言。** 曾有一次中文提問得到英文回覆，SKILL.md 已補上規則。
- **未驗證：**
  - 「不參考其他角色」：沙盒裡沒有範例可找，所以沒測到。
  - 在使用者的真實專案資料夾（有其他角色）裡的行為。
- **標準化建議：**
  - 把 c2s 打包成可獨立安裝的指令，目前沙盒仍依賴本專案的 `.venv`（K-26）。
  - SKILL.md 的範例改為不含座標的結構示意，避免 Agent 照抄。
  - 每次執行輸出一份給使用者的摘要，固定欄位：狀態、需人工清單、預覽路徑。
  - 標準化之後，用使用者自己的 3D 算圖風角色建立新的保留集再驗收。

**待使用者決定：**

- 是否親自目視 `output/generalization/<案例>/visual_sheet.png`，填入使用者目視欄。`docs/` 裡的是縮小版，sha256 不同，不能作為目視紀錄綁定的對象。
- 是否提供自己的角色圖，作為下一輪保留集。
- D-36 的取捨：需人工的草稿在補畫前不露出（目前），或是優先保留手臂動作。
